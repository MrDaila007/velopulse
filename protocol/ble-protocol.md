# BLE-протокол Bike Computer

Версия протокола: **1.2** · Роли: устройство — **Peripheral** (приложение) и
**Central** (BLE CSC: CYCPLUS C3/S3); приложение — **Central** к BikeComp

Связанные документы: [`uuids.md`](uuids.md) — реестр UUID,
[`data-structures.md`](data-structures.md) — байтовые раскладки.

Требования-источники: ТЗ §11–§17, §30, §32, §33.

---

## 1. Обзор

Устройство публикует один собственный GATT-сервис **Bike Computer Configuration Service**
с семью характеристиками (одна опциональная). Обмен — бинарный, little-endian,
структуры фиксированного размера с версионированием.

```text
┌──────────────────────────── Bike Computer (Peripheral) ────────────────────────────┐
│ Service 7C9A0001-…                                                                 │
│  ├── 0002 Device Information   R          48 B   модель, версии, uptime, serial     │
│  ├── 0003 Telemetry            R + N   36/44 B   скорость, дистанция, АКБ, CSC     │
│  ├── 0004 Config Read          R + N      48 B   актуальная конфигурация            │
│  ├── 0005 Config Write         W(resp)    48 B   новая конфигурация (транзакция)    │
│  ├── 0006 Command              W(resp)   4-20 B  команды управления                 │
│  ├── 0007 Command Result       R + N     9-25 B  статус последней операции          │
│  └── 0008 Error Log            R + N   (опц.)    журнал событий                     │
└────────────────────────────────────────────────────────────────────────────────────┘
```

Разделение чтения и записи конфигурации на две характеристики (`0004`/`0005`) сделано
осознанно: это позволяет применять разные требования безопасности (чтение — по шифрованию,
запись — только bonded), исключает гонку «клиент пишет / устройство обновляет значение для
чтения» и делает журналирование записей однозначным.

## 2. Версионирование (ТЗ §32)

Формат `major.minor`, передаётся в Device Information.

| Изменение | Инкремент | Пример |
| --- | --- | --- |
| Удаление/переопределение поля, смена UUID, смена семантики | `major` | 1.0 → 2.0 |
| Добавление поля в конец структуры, новая команда, новая характеристика | `minor` | 1.0 → 1.1 |

### Правила совместимости на стороне приложения

```text
device.proto_major == app.proto_major  →  полная работа
device.proto_minor >  app.proto_minor  →  работа, неизвестные поля/команды игнорируются
device.proto_minor <  app.proto_minor  →  работа, новые функции скрыты в UI
device.proto_major != app.proto_major  →  ЧТЕНИЕ Device Information разрешено,
                                          запись конфигурации и команды ЗАБЛОКИРОВАНЫ,
                                          пользователь видит предупреждение
```

Проверка версии выполняется **первым действием** после подключения, до любых записей.

## 3. Реклама и обнаружение

| Параметр | Значение |
| --- | --- |
| Быстрая реклама | интервал 30 мс, 30 с после старта/пробуждения |
| Медленная реклама | интервал 1000 мс, постоянно (`ble_always_advertise = true`) |
| Имя | `BikeComp-XXXX` (XXXX — 4 hex-символа serial), настраивается |
| ADV payload | Flags + 128-bit Service UUID |
| Scan Response | Complete Local Name, Tx Power |
| Tx Power | +4 dBm |

Service UUID остаётся авторитетным признаком совместимости (ТЗ §21). Для обхода
ошибок Android native scan filter приложение может запрашивать нефильтрованный scan
и фильтровать результаты локально. `BikeComp-*` допустим только как discovery fallback,
если Android не вернул список advertised UUID; до завершения GATT discovery такое
устройство считается лишь кандидатом и не получает доступ к рабочим экранам.

## 4. Параметры соединения

| Параметр | Значение | Обоснование |
| --- | --- | --- |
| Connection Interval | 15…60 мс (запрос устройства) | Компромисс отклик/потребление |
| Slave Latency | 0 | Быстрый отклик на команды |
| Supervision Timeout | 4 с | Быстрое обнаружение разрыва |
| ATT MTU | запрос 247, минимум 51 | Одна структура — один пакет |
| Data Length Extension | включено, если поддержано телефоном | Меньше накладных расходов |
| Максимум соединений | 1 | Устройство обслуживает один телефон |

## 5. Основные сценарии

### 5.1. Подключение и первичная синхронизация

```text
App                                          Device
 │ scan (локальный UUID/default-name filter)    │  реклама
 │────────────────────────────────────────────▶│
 │ connect                                     │
 │────────────────────────────────────────────▶│
 │ MTU exchange (247)                          │
 │◀───────────────────────────────────────────▶│
 │ discover services / characteristics         │
 │◀───────────────────────────────────────────▶│
 │ read Device Information                     │
 │────────────────────────────────────────────▶│
 │◀── proto 1.0, fw 1.0.0, flags ──────────────│
 │ [проверка совместимости версии]             │
 │ pairing/bonding (если ещё нет bond)          │
 │◀───────────────────────────────────────────▶│
 │ read Config Read                            │
 │────────────────────────────────────────────▶│
 │◀── Configuration (48 B) ────────────────────│
 │ [только после успешного encrypted read]     │
 │ subscribe Telemetry, Config Read, Cmd Result│
 │────────────────────────────────────────────▶│
 │◀── Telemetry notify 1 Гц ───────────────────│
```

### 5.2. Изменение настройки (write-then-verify, ТЗ §30, §31)

```text
App                                          Device
 │ [локальная валидация полей]                 │
 │ write Config Write (48 B, w/ response)      │
 │────────────────────────────────────────────▶│  валидация всех полей
 │                                             │  → сохранение в Flash (A/B + CRC)
 │                                             │  → применение (ISR, контраст, тайм-ауты)
 │◀── Cmd Result{id=0xF0, status=OK} ──────────│
 │◀── notify Config Read (факт. конфигурация) ─│
 │ [сверка отправленного и полученного]        │
```

Правила:
* Приложение **не считает** запись успешной до `Command Result{status=OK}` (ТЗ §30).
* При `ERR_RANGE` приложение подсвечивает поле по `detail` (смещение поля) и не сбрасывает
  черновик пользователя.
* Тайм-аут ответа — 3 с; при отсутствии ответа запись помечается «неизвестный результат»,
  выполняется повторное чтение конфигурации для определения фактического состояния.
* Конфигурация всегда пишется целиком: приложение читает актуальную, накладывает изменения
  пользователя и отправляет полную структуру. Это исключает частичные состояния.

### 5.3. Безопасная команда

```text
 │ write Command{id=RESET_TRIP}                │
 │────────────────────────────────────────────▶│  сброс trip/avg/max/moving_time
 │◀── Cmd Result{status=OK} ───────────────────│
 │◀── Telemetry notify (нулевые счётчики) ─────│
```

### 5.4. Опасная команда (двухфазное подтверждение)

Полная диаграмма — в [`data-structures.md` §5.2](data-structures.md#52-протокол-подтверждения-опасных-команд-тз-16-28).
Требования UI (ТЗ §28): отдельное предупреждение → повторное подтверждение → ввод слова
подтверждения (`СБРОС` / `RESET`) либо длительное удержание кнопки.

### 5.5. Тест датчика (ТЗ §24)

```text
 │ Command{SENSOR_TEST_START, duration=60}     │
 │────────────────────────────────────────────▶│  режим теста: телеметрия 5 Гц
 │◀── Telemetry @5 Гц (revolutions, age, lvl) ─│
 │ [UI: индикатор прохождения магнита,         │
 │  счётчик импульсов, тестовая скорость]      │
 │ Command{SENSOR_TEST_STOP}                   │
 │────────────────────────────────────────────▶│
 │◀── Cmd Result{status=OK} ───────────────────│
```

### 5.6. Разрыв и восстановление (ТЗ §30)

```text
 разрыв ──▶ показать статус «отключено»
        ──▶ сохранить черновик несохранённых настроек в памяти приложения
        ──▶ авто-переподключение: 1 с, 2 с, 4 с, 8 с, далее каждые 15 с
        ──▶ после подключения: read Device Info → read Config → resubscribe
        ──▶ если черновик отличается от прочитанной конфигурации,
            предложить «применить несохранённые изменения»
```

Устройство при разрыве: аннулирует активный nonce, завершает режим теста датчика,
возвращается к штатной частоте телеметрии, возобновляет рекламу, продолжает считать
поездку (ТЗ §29).

## 6. Частота уведомлений и энергопотребление (ТЗ §14)

| Ситуация | Telemetry notify |
| --- | --- |
| Открыт экран мониторинга | 1 Гц |
| Режим теста датчика | 5 Гц |
| Приложение в фоне | 0.2 Гц (приложение отписывается или снижает частоту) |
| Нет подписки | значение обновляется 0.2 Гц только для Read |

Приложение обязано отписываться от Telemetry при переходе в фон и на экраны, где
телеметрия не отображается.

## 7. Безопасность (ТЗ §17)

| Механизм | v1.0 |
| --- | --- |
| Pairing | LESC Just Works (устройство без ввода/вывода) |
| Bonding | обязательно, ключи в Flash |
| Шифрование | обязательно для Config Write, Command, Config Read, Telemetry |
| Окно нового сопряжения | 5 минут после включения |
| После окна | принимаются только ранее сохранённые связи |
| Повторное открытие окна | USB-команда `open-pairing`, `CMD_OPEN_PAIRING_WINDOW` (с bonded-устройства), либо `FACTORY_RESET` |
| Число доверенных устройств | до 4 bond'ов (замена по LRU) |
| Прототип | `FEATURE_OPEN_PAIRING=1` — постоянная возможность сопряжения |

Опции, не входящие в v1.0 (архитектурно допустимы): PIN-код, ограничение единственным
доверенным устройством, подтверждение сопряжения через USB.

Приложение при `ERR_NOT_PAIRED` показывает инструкцию: «выключите и включите устройство,
затем подключитесь в течение 5 минут».

## 8. Обработка ошибок — контракт для приложения

| Ситуация | Поведение приложения |
| --- | --- |
| Сервис не найден после подключения | Отключиться, сообщить «устройство не поддерживается» |
| MTU < 51 | Режим «только чтение», предупреждение |
| `major` не совпадает | Блокировать запись, показать требование обновления |
| `ERR_RANGE` | Подсветить поле, не терять черновик |
| `ERR_BUSY` | До 3 повторов с интервалом 1 с |
| `ERR_STORAGE` | Показать ошибку, предложить повтор; не считать настройку применённой |
| Нет ответа 3 с | Перечитать конфигурацию, показать «результат неизвестен» |
| Разрыв во время записи | После восстановления перечитать конфигурацию и сравнить |

## 9. Что протокол не делает в v1.0

* Не передаёт историю поездок и треки (зарезервирован UUID `…0009`).
* Не поддерживает OTA/DFU в собственном сервисе — планируется штатный Nordic Secure DFU
  (зарезервирован UUID `…000A` под метаданные).
* Не фрагментирует пакеты: все структуры умещаются в один ATT-пакет при MTU ≥ 51.
* Не использует Bluetooth CSC Profile как **peripheral** (BikeComp не публикует `0x1816`
  для Strava/Zwift). Причина — ADR-013.

## 10. BLE CSC central (протокол 1.2)

BikeComp одновременно остаётся peripheral для приложения и подключается как central
к одному датчику Cycling Speed and Cadence (`0x1816` / Measurement `0x2A5B`).

| Датчик | Рекламное имя | CSC flags | Что считает BikeComp |
| --- | --- | --- | --- |
| CYCPLUS C3 | `CYCPLUS C3` | crank | каденс, OLED-страница CAD, `cadence_x10` |
| CYCPLUS S3 | `CYCPLUS S3` | wheel | скорость, поездка и одометр (синтетические обороты) |

Один физический Cycplus C3/S3 не умеет оба режима сразу: переключатель C/S меняет
роль. Адрес BLE тот же, повторный pairing не нужен. ANT+ не используется
(SoftDevice S140, см. ADR-014).

Сопряжение CSC: 90 с после boot без bond, либо Serial `csc-pair`. Bond хранится в
`/csc_a` `/csc_b`. `csc-forget` и factory reset стирают bond. Пока S3 — источник
скорости, Hall не дублирует дистанцию; после 4 с тишины Hall снова активен.
Окружность колеса для S3 берётся из `wheel_circumference_mm` BikeComp, не из
настройки датчика.
