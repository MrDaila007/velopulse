# 06. Тестирование и приёмка

Документ описывает уровни тестирования, стенды, методики измерений и трассировку всех
критериев приёмки ТЗ §42–§43 на конкретные проверки.

---

## 1. Пирамида тестирования

```text
                    ┌─────────────────────────────┐
                    │  Полевые испытания (3+)     │  реальные поездки ≥ 60 км
                    ├─────────────────────────────┤
                    │  Приёмочные сценарии (32)   │  ТЗ §42 (17) + §43 (15)
                    ├─────────────────────────────┤
                    │  Интеграционные (стенд)     │  устройство + телефон
                    ├─────────────────────────────┤
                    │  Embedded-тесты на железе   │  I²C, Flash, ADC, ISR
                    ├─────────────────────────────┤
                    │  Host-тесты домена (native) │  математика, фильтры, FSM, кодеки
                    └─────────────────────────────┘
```

Принцип: всё, что можно проверить без железа — проверяется без железа. Домен прошивки
компилируется на хосте, приложение работает против `FakeBleTransport`.

## 2. Host-тесты прошивки (`pio test -e native`)

| Модуль | Тестовые случаи |
| --- | --- |
| `crc32` | Эталонные векторы (`"123456789"` → `0xCBF43926`), пустой ввод |
| `PulseFilter` | Отбраковка по debounce; отбраковка по превышению лимита скорости; корректный импульс на границе допустимого интервала; детектор залипания; переполнение `micros()` во время интервала |
| `SpeedCalculator` | Пример из ТЗ (C=2100, dt=300 мс → 25.2 км/ч); граничные окружности 500 и 3000 мм; скорость при dt на пределе лимита; тайм-аут → 0.0; сглаживание по 2/3/5 интервалам; сглаживание при неполном окне |
| `TripComputer` | Накопление дистанции без потери точности на 1 000 000 оборотов; avg при `moving_time = 0`; avg на большой дистанции (проверка `uint64`); обновление max; сброс поездки обнуляет trip/avg/max/moving_time и **не трогает** одометр |
| `Odometer` | Переполнение `uint32` в метрах не наступает; конвертация мм → м → км |
| `RideState` | IDLE→MOVING по первому импульсу; MOVING→PAUSED по тайм-ауту; PAUSED→MOVING; moving_time не растёт в PAUSED |
| `PageCarousel` | Переключение по периоду; пропуск отключённых страниц; пустая маска → страница 0; закреплённая страница при выключенной карусели; произвольный `page_order` |
| `BatteryModel` | Интерполяция таблицы SoC на всех узлах и между ними; клиппинг вне диапазона; монотонность процента без зарядки; рост процента при зарядке |
| `ConfigValidator` | Каждое поле: min−1, min, середина, max, max+1; `display_timeout = 0` (никогда) валиден; пустая маска страниц невалидна; `page_order` с повтором невалиден; имя устройства: 2 символа, 15 символов, 16 символов, запрещённый символ |
| `ProtocolCodec` | Round-trip всех структур; совпадение с фикстурами байт-в-байт; чтение структуры с большим `struct_version`; отказ при неверной длине |
| `Scheduler` | Срабатывание по периоду; корректность при переполнении `millis()` (тест с искусственным `now = 0xFFFFFF00`) |

Целевое покрытие домена: **≥ 85 %** строк.

## 4. Стенды

### 4.1. Стенд импульсов (обязателен)

Два варианта, лучше иметь оба:

1. **Электронный**: второй микроконтроллер (или второй XIAO) генерирует импульсы заданной
   частоты на вход D0. Позволяет точно задать эквивалентную скорость и проверить
   погрешность расчёта. Формула: `f = V_kmh / (C_mm × 0.0036)`, т. е. для C = 2100 мм и
   V = 25 км/ч → `f = 3.31 Гц` (интервал 302 мс).
2. **Механический**: колесо на подставке с магнитом и датчиком. Проверяет реальную
   магнитную картину, вибрации, зазор, отсутствие двойных срабатываний.

### 4.2. Стенд измерения тока

Мультиметр в режиме мкА/мА в разрыве питания батареи, либо USB-power-meter для зарядки.
Для корректного измерения idle нужен прибор с разрешением 10 мкА.

### 4.3. Эталон дистанции

Разметка 100 м на ровной поверхности (рулетка/дальномер) + GPS-трек поездки для дистанций
> 10 км.

## 5. Методики измерений

### 5.1. Погрешность скорости (ТЗ §42.5, критерий ≤ 2 %)

1. На электронном стенде задать частоту, соответствующую 10, 25, 40, 60 км/ч при
   C = 2100 мм.
2. Для каждой точки: 60 с измерения, зафиксировать показания устройства (по телеметрии,
   не по экрану — выше разрешение).
3. Погрешность = `|V_изм − V_эталон| / V_эталон × 100 %`.
4. Повторить при C = 500 мм и C = 3000 мм для крайних настроек.
5. **Критерий**: во всех точках ≤ 2 %; фактически при точной окружности ожидается < 0.5 %,
   поскольку арифметика целочисленная и детерминированная. Основной вклад в реальную
   погрешность даёт неточность окружности колеса — это отражается в инструкции пользователя.

### 5.2. Регистрация каждого оборота (ТЗ §42.3)

1. Медленно (≈ 5 км/ч) прокрутить колесо ровно 100 оборотов, считая вслух.
2. Сверить `revolutions` в телеметрии: должно быть ровно 100.
3. Повторить на скорости ≈ 40 км/ч (раскрутка колеса) с подсчётом по метке/видеозаписи.
4. Повторить при зазорах 2 мм и 8 мм.
5. **Критерий**: расхождение 0 на всех прогонах.

### 5.3. Фильтрация ложных импульсов (ТЗ §42.4)

1. Остановить колесо так, чтобы магнит находился напротив датчика; выдержать 60 с.
   Ожидание: не более одного оборота начислено, состояние `SENSOR_STUCK` при залипании.
2. Постучать по вилке и потрясти велосипед 60 с без вращения колеса.
   Ожидание: `revolutions` не изменился, дистанция не выросла.
3. Подать на вход двойные импульсы с интервалом 2 мс (стенд).
   Ожидание: засчитан один, `rejected_debounce` увеличился.
4. Подать импульсы, соответствующие 150 км/ч при лимите 100.
   Ожидание: отброшены, `rejected_overspeed` увеличился.

### 5.4. Сохранность данных (ТЗ §42.6, §42.7)

1. Накатать 2.0 км, зафиксировать trip и одометр.
2. Отключить питание (снять АКБ) без корректного завершения.
3. Включить: одометр = зафиксированный ± ≤ 500 м (интервал записи), настройки целы.
4. Выполнить `RESET_TRIP`: trip = 0, одометр не изменился.
5. Выполнить `RESET_ODOMETER` с подтверждением: одометр = 0.

### 5.5. Автономность

1. Полный заряд, отключить USB.
2. Сценарий А (движение): непрерывная генерация импульсов 25 км/ч до отключения.
   Фиксировать время. Ожидание ≥ 20 ч (цель 40+).
3. Сценарий Б (idle): без импульсов, OLED выключен, реклама медленная. Измерить средний
   ток. Ожидание ≤ 1.5 мА.
4. Занести фактические значения в `docs/05-hardware-design.md §6`.

### 5.6. Стабильность BLE

1. 100 циклов «подключение → чтение конфигурации → отключение» скриптом/приложением.
   Ожидание: 100 успешных, без зависаний устройства.
2. Длительное соединение 2 ч с телеметрией 1 Гц. Ожидание: нет разрывов сверх
   3 (переподключения допустимы), `seq` без пропусков > 1 %.
3. Уход из зоны действия и возврат: приложение переподключается автоматически.
4. Перезагрузка телефона при активном bond: подключение восстанавливается без повторного
   сопряжения.

## 6. Трассировка критериев приёмки прошивки (ТЗ §42)

| № | Критерий | Метод проверки | Артефакт |
| --: | --- | --- | --- |
| 1 | Устройство стабильно запускается | 20 циклов включения; проверка `boot_count`, отсутствие reset по watchdog | Протокол, счётчики |
| 2 | SSD1306 отображает данные | Визуальная проверка обеих геометрий: 5 страниц, постоянная скорость/батарея, splash | Фото |
| 3 | Каждый оборот регистрируется один раз | §5.2 | Протокол |
| 4 | Ложные импульсы фильтруются | §5.3 | Счётчики отбраковки |
| 5 | Погрешность скорости ≤ 2 % | §5.1 | Таблица измерений |
| 6 | Дистанция сохраняется после перезагрузки | §5.4 п.1–3 | Протокол |
| 7 | Одометр не сбрасывается при сбросе поездки | §5.4 п.4 | Протокол |
| 8 | Автоматический старт работает | Первый импульс после простоя → MOVING < 1 с | Телеметрия |
| 9 | Автоматическая пауза работает | Прекращение импульсов → скорость 0 и остановка moving_time через `stop_timeout` ± 0.3 с | Телеметрия |
| 10 | OLED выключается после остановки | Тайм-аут 10 с (для теста) и 60 с (default) | Наблюдение + `display_on` |
| 10a | OLED защищён от статичного изображения | Оставить экран включённым > 4 мин; подтвердить четыре позиции сдвига и возврат к исходной | Наблюдение/видео |
| 11 | Новый оборот включает OLED | Импульс при выключенном экране → включение < 300 мс | Наблюдение |
| 12 | Уровень аккумулятора отображается | Сверка с мультиметром при 3 уровнях заряда | Таблица |
| 13 | Устройство доступно по BLE | Обнаружение по Service UUID с 5 м; подключение | Скриншот |
| 14 | Настройки читаются и записываются | Изменение всех полей конфигурации по одному, проверка применения | Протокол |
| 15 | Некорректные настройки отклоняются | Запись значений вне диапазона по каждому полю (min−1, max+1) → `ERR_RANGE` + верный `field_id` | Протокол |
| 16 | Сброс поездки выполняется через BLE | Команда `RESET_TRIP` → нулевые счётчики | Телеметрия |
| 17 | Прошивка считает поездку без телефона | 2 км без подключения, затем подключение и сверка | Протокол |

## 8. Полевые испытания

| Параметр | Требование |
| --- | --- |
| Количество поездок | ≥ 3 |
| Суммарная дистанция | ≥ 60 км |
| Условия | Асфальт + неровности; одна поездка в дождь или после дождя |
| Что фиксируем | Дистанция по устройству vs GPS; максимальная скорость (адекватность); число перезагрузок; счётчики отбраковки импульсов; заряд до/после |
| Критерии | Расхождение дистанции с GPS ≤ 2 %; нет перезагрузок; нет неадекватных выбросов max speed; магнит и датчик не сместились |

Форма протокола полевых испытаний:

```text
Дата / маршрут / погода:
Дистанция устройство / GPS / расхождение %:
Max speed устройство / адекватность:
Обороты (revolutions):
rejected_debounce / rejected_overspeed / isr_overflow:
boot_count до / после:
Заряд до / после:
Замечания:
```

## 9. Регрессия перед релизом

Полный прогон занимает ~1 день:

1. `pio test -e native` + сборка обоих OLED-профилей + `pio test -e xiao_ble_sense` — зелёные.
2. `flutter test` + `flutter analyze` — зелёные.
3. Приёмочные сценарии §6 и §7 — 32 пункта.
4. Автономность (§5.5, сценарий Б — измерение тока, 30 мин достаточно для оценки).
5. Стабильность BLE (§5.6 п.1 — 100 циклов, автоматизируется скриптом).
6. Одна контрольная поездка ≥ 10 км.
7. Сверка `protocol/*` с кодом (golden-тесты обеих сторон на общих фикстурах).
