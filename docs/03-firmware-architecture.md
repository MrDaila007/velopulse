# 03. Архитектура прошивки

Целевая платформа: **Seeed Studio XIAO nRF52840 Sense** (Nordic nRF52840, Cortex-M4F,
256 КБ RAM, 1 МБ Flash + 2 МБ внешней QSPI).
Среда: **PlatformIO**, framework **Arduino** (Adafruit nRF52 core), **C++17**.

Требования-источники: ТЗ §3–§10, §42.

---

## 1. Слои и зависимости

Зависимости направлены строго вниз. Домен не знает ни про Arduino, ни про U8g2, ни про BLE —
это делает его тестируемым на хосте (`pio test -e native`).

```text
┌──────────────────────────────────────────────────────────────────┐
│ APP        main.cpp · Scheduler · AppController (FSM) · Events   │
└───────────────┬──────────────────────────────────┬───────────────┘
                │                                  │
┌───────────────▼──────────────────┐  ┌────────────▼───────────────┐
│ DOMAIN (чистый C++, без Arduino) │  │ SERVICES (адаптеры)        │
│  PulseFilter                     │  │  DisplayManager  (U8g2)    │
│  SpeedCalculator                 │  │  BleManager      (Bluefruit)│
│  TripComputer                    │  │  StorageManager  (LittleFS)│
│  Odometer                        │  │  BatteryManager  (ADC)     │
│  BatteryModel (SoC LUT)          │  │  WheelSensor     (GPIO IRQ)│
│  ConfigModel + Validator         │  │  DiagnosticsService        │
│  PageCarousel                    │  │  TimeSource / Watchdog     │
│  ProtocolCodec (сериализация)    │  │                            │
└───────────────┬──────────────────┘  └────────────┬───────────────┘
                └──────────────┬───────────────────┘
                ┌──────────────▼───────────────────┐
                │ HAL / BSP  board_pins.h · Arduino│
                │ core · nrfx · Adafruit_LittleFS  │
                └──────────────────────────────────┘
```

### Правила слоёв

* `lib/domain/` компилируется без Arduino.h → покрывается host-тестами.
* Сервисы получают зависимости через конструктор/`begin(...)`, никаких глобальных синглтонов
  кроме `app` в `main.cpp`.
* Обмен между сервисами — через `AppController` и типизированные события, а не
  прямыми вызовами друг друга (исключение: `DisplayManager` читает снимок данных).

## 4. Кооперативный планировщик

Никаких `delay()` в `loop()` (ТЗ §3.4). Планировщик — таблица задач с периодом и
дедлайном на `millis()`.

```cpp
struct Task {
    const char* name;
    uint32_t    period_ms;     // 0 = каждый цикл
    uint32_t    next_due_ms;
    void      (*run)(AppController&);
    uint16_t    max_runtime_us; // измеряется, попадает в диагностику
};
```

| Задача | Период | Назначение |
| --- | --- | --- |
| `task_pulses` | каждый цикл | Выборка импульсов из ring buffer, фильтр, расчёты |
| `task_state` | 100 мс | FSM: автопауза, тайм-ауты, переходы режимов |
| `task_display` | 250 мс / 1000 мс | Рендер (частота зависит от состояния, ТЗ §7.1) |
| `task_battery` | 1000 мс (измерение), 10 с (пересчёт %) | ADC + фильтр |
| `task_ble_notify` | 1000 мс (или по подписке) | Telemetry notify (ТЗ §14) |
| `task_storage` | 1000 мс | Проверка условий записи одометра (ТЗ §9.2) |
| `task_watchdog` | 500 мс | Кормление WDT, контроль зависаний |
| `task_diag` | 5000 мс | Uptime, счётчики, свободная память |

Правила:

* Бюджет одного вызова любой задачи — **≤ 5 мс**; рендер OLED (самая тяжёлая, ~15–25 мс на
  I²C 400 кГц для 512 байт) разбивается на две фазы: подготовка буфера и `sendBuffer()`.
* Все временные метки — `uint32_t`, сравнение только через разность:
  `(int32_t)(now - due) >= 0`. Это корректно при переполнении `millis()` через 49.7 дней.
* Планировщик логирует превышение дедлайна > 50 мс в `diagnostics.late_task_count`.

## 5. Модуль WheelSensor (датчик Холла)

### 5.1. ISR

```cpp
// ISR: только сохранить время, инкремент, флаг. Запрещено: дисплей, Flash, BLE,
// float, Serial (ТЗ §3.4).
static volatile uint32_t s_ts_buf[PULSE_BUF_SIZE];   // PULSE_BUF_SIZE = 8 (степень 2)
static volatile uint8_t  s_head = 0;                 // пишет только ISR
static volatile uint8_t  s_tail = 0;                 // читает только loop
static volatile uint32_t s_raw_pulse_count = 0;
static volatile uint8_t  s_pin_level_snapshot = 0;

void WheelSensor::isr() {
    uint32_t now = micros();
    uint8_t  next = (uint8_t)((s_head + 1) & (PULSE_BUF_SIZE - 1));
    if (next != s_tail) {           // переполнение = теряем импульс, но не блокируем ISR
        s_ts_buf[s_head] = now;
        s_head = next;
    } else {
        s_overflow_count++;
    }
    s_raw_pulse_count++;
}
```

* Ring buffer single-producer/single-consumer, `head`/`tail` — однобайтовые volatile,
  запись/чтение атомарны на Cortex-M. Критические секции не нужны.
* Аппаратный фильтр: `attachInterrupt(digitalPinToInterrupt(PIN_HALL), isr, edge)`,
  где `edge` берётся из конфига (`FALLING` по умолчанию для open-drain + `INPUT_PULLUP`).
* Настройка `sensor_invert` меняет активный фронт без перепрошивки (ТЗ §24).

### 5.2. Фильтрация (ТЗ §4.3)

Три независимых фильтра, применяются последовательно в `task_pulses`:

1. **Debounce**: `dt < debounce_us` → отбросить (`debounce_ms` из конфига, 0…50, по умолчанию 3 мс).
2. **Минимальный интервал по лимиту скорости**:
   `dt_min_ms = (circumference_mm * 36) / (max_speed_kmh * 10)`
   Для C = 2100 мм и V = 100 км/ч → 75 мс. Импульсы быстрее — отбрасываются.
3. **Sanity-фильтр «залипания»**: если между двумя импульсами уровень пина не вернулся в
   пассивное состояние дольше `stuck_timeout_ms` (500 мс), помечаем датчик как
   `SENSOR_STUCK` и не начисляем оборот (магнит остановился напротив датчика).

Счётчики каждого фильтра доступны в диагностике: `rejected_debounce`, `rejected_overspeed`,
`rejected_stuck`, `isr_overflow`.

### 5.3. Состояние датчика

`SENSOR_OK` (импульс за последние 10 с) → `SENSOR_IDLE` (нет импульсов, штатно) →
`SENSOR_STUCK` (постоянный активный уровень) → `SENSOR_NO_SIGNAL` (никогда не было
импульсов после старта). Передаётся в телеметрию (ТЗ §14) и отображается на экране (ТЗ §6).

## 6. Расчёт скорости и дистанции

### 6.1. Формулы в фиксированной точке

Базовое соотношение ТЗ §4.2: `speed_kmh = C_mm × 3.6 / dt_ms`.

В единицах `0.01 км/ч` с интервалом в микросекундах:

```text
speed_x100 = (C_mm * 360000UL) / dt_us
```

Проверка размерности и переполнения: максимум числителя `3000 × 360000 = 1.08e9` —
входит в `uint32_t` (4.29e9). Пример: C = 2100, dt = 300000 мкс → `2100*360000/300000 = 2520`
→ 25.20 км/ч (совпадает с формулой ТЗ: `2100×3.6/300 = 25.2`).

Минимальный интервал (для фильтра): `dt_min_us = (C_mm * 360000UL) / (max_speed_kmh * 100)`.

### 6.2. Сглаживание (ТЗ §4.5)

Скользящее среднее по последним N интервалам (N = `smoothing_window`, 2…5, по умолчанию 3),
отключаемое флагом `smoothing_enabled`:

```text
speed_x100 = (C_mm * 360000UL * N) / (dt_1 + dt_2 + ... + dt_N)
```

Усредняются **интервалы**, а не скорости — это математически корректнее (гармоническое
среднее) и дешевле. При заполнении окна меньше N используется фактическое число выборок.

### 6.3. Дистанция (ТЗ §4.4)

```cpp
trip_revolutions++;                       // uint32
trip_distance_mm += cfg.circumference_mm; // uint32, 4.29e9 мм = 4295 км на поездку
odometer_mm      += cfg.circumference_mm; // uint64
```

Хранение в целых миллиметрах исключает накопление ошибки. Перевод в км — только при выводе:
`km_x100 = trip_distance_mm / 10000`.

**Важно:** при изменении окружности колеса ранее пройденная дистанция не пересчитывается;
новое значение применяется только к последующим оборотам.

### 6.4. Средняя и максимальная скорость

```text
avg_speed_x100 = (trip_distance_mm * 360UL) / moving_time_ms       // при moving_time_ms > 0
```
Проверка переполнения: при большой дистанции числитель выходит за `uint32` →
расчёт выполняется в `uint64_t` (`(uint64_t)trip_mm * 360 / moving_ms`), это редкая
операция (1 раз в 250 мс), стоимость несущественна.

`max_speed_x100 = max(max_speed_x100, speed_x100)` — обновляется только по корректному
импульсу, живёт до сброса поездки (ТЗ §5.4).

## 7. Конечный автомат поездки и питания

ТЗ §5 (поездка) и §10 (энергосбережение) описывают два ортогональных аспекта. Реализуем
**два связанных автомата**: `RideState` и `PowerState`.

### 7.1. RideState

```text
        первый корректный импульс
  IDLE ─────────────────────────────▶ MOVING
   ▲                                    │  нет импульсов > stop_timeout_s (3 с)
   │  сброс поездки / нет движения      ▼
   └──────────────────────────── PAUSED
             корректный импульс ──▶ MOVING
```

| Состояние | speed | moving_time | Экран |
| --- | --- | --- | --- |
| `IDLE` | 0.0 | не растёт | обновление 1 Гц, гаснет по display_timeout |
| `MOVING` | расчётная | растёт | обновление 4 Гц |
| `PAUSED` | 0.0 | **не растёт** (ТЗ §5.2) | обновление 1 Гц |

`moving_time_ms` инкрементируется в `task_state` только в состоянии `MOVING`, приращением
`now - last_state_tick_ms`. Это исключает как дрейф, так и учёт времени стоянки.

### 7.2. PowerState (ТЗ §10.1)

```text
                 ┌──────────── USB подключён ────────────┐
                 ▼                                        │
            [CHARGING] ──── USB отключён ────▶ (возврат в предыдущее)
                 
[BOOT] ─▶ [ACTIVE] ──нет движения 3 с──▶ [SHORT_STOP]
             ▲                                │ display_timeout (60 с)
             │                                ▼
             ├───── импульс/BLE ────────── [IDLE_DISPLAY_OFF]
             │                                │ deep_sleep_timeout (15 мин)
             │                                ▼
             └───── импульс/USB ───────── [DEEP_SLEEP]

[BLE_CONFIG] — накладывается на ACTIVE/SHORT_STOP/IDLE при активном соединении:
               дисплей принудительно включён, notify активны, sleep заблокирован.
```

Правила переходов:

* `ACTIVE → SHORT_STOP`: нет импульсов `stop_timeout_s`.
* После половины `display_timeout_s` без корректных импульсов OLED переходит в
  приглушённый режим; содержимое и частота обновления не меняются.
* `SHORT_STOP → IDLE_DISPLAY_OFF`: истёк полный `display_timeout_s` (0 = «никогда»).
  Перед выключением дисплея — принудительная запись одометра (ТЗ §9.2).
* `IDLE_DISPLAY_OFF → DEEP_SLEEP`: истёк `deep_sleep_timeout_s`; при `FEATURE_DEEP_SLEEP=0`
  переход заменяется на «низкочастотный idle» (loop 10 Гц, медленная реклама).
* Пробуждение из `DEEP_SLEEP`: GPIO SENSE на пине Холла, подключение USB (ТЗ §10.2).
* `CHARGING` определяется по `PIN_CHG` + наличию VBUS; в этом состоянии deep sleep запрещён,
  дисплей показывает индикацию заряда.

### 7.3. Реализация глубокого сна

Архитектурно предусмотрен интерфейс `PowerManager::enterDeepSleep()`; в v1.0 за флагом
`FEATURE_DEEP_SLEEP` (по умолчанию **выключен**, ТЗ §10.2 это допускает). Внутри:
`sd_power_system_off()` с предварительной настройкой `nrf_gpio_cfg_sense_input` на пине
Холла и записью всех персистентных данных. Пробуждение = аппаратный reset → при старте
`reset_reason` показывает `WAKE_FROM_SLEEP`, счётчики восстанавливаются из Flash.

## 8. DisplayManager

### 8.1. Драйвер и профили сборки

Высота задаётся compile-time макросом `BIKECOMP_DISPLAY_HEIGHT`; допустимы только
`32` и `64`. Автоопределение невозможно, потому что обе панели используют тот же
контроллер и I²C-адрес.

```cpp
// xiao_ble_sense, основной профиль
U8G2_SSD1306_128X64_NONAME_F_HW_I2C u8g2(U8G2_R0, U8X8_PIN_NONE);

// xiao_ble_sense_128x32, совместимый профиль
U8G2_SSD1306_128X32_UNIVISION_F_HW_I2C u8g2(U8G2_R0, U8X8_PIN_NONE);
```

Полный буфер (`_F_`) занимает 1024 байта для 128×64 и 512 байт для 128×32.
Адрес обеих панелей — `0x3C`, I²C работает на 400 кГц. BLE-протокол и
`DeviceConfig` от выбора панели не зависят.

### 8.2. Компоновки 128×64 и 128×32

Основной профиль 128×64 делится на три зоны:

```text
┌────────────────────────────────────────────────────────────┐
│ km/h                                           [BAT][82%]  │ y 0..10
│ 24.8                                                       │ y 11..47
│ MOV TRIP 18.42 km                                          │ y 50..63
└────────────────────────────────────────────────────────────┘
```

* Скорость: `u8g2_font_logisoso38_tn`, значения до `200.0` помещаются целиком.
* Метрика: `u8g2_font_6x13_tf`; строки длиннее 21 символа переключаются на `5x8`.
* `LOW BATT` инвертирует всю нижнюю зону 128×14.
* Совместимый профиль 128×32 сохраняет прежние координаты, Logisoso 20 и нижнюю
  строку `5x8` пиксель-в-пиксель.
* Splash и три test pattern используют фактическую высоту выбранной панели.

### 8.3. Страницы карусели (ТЗ §6.2)

| ID | Бит маски | Содержимое | Формат |
| --- | --- | --- | --- |
| 0 | 0x01 | Дистанция поездки | `MOV TRIP 18.42 km` |
| 1 | 0x02 | Средняя скорость | `MOV AVG 19.7 km/h` |
| 2 | 0x04 | Максимальная скорость | `MOV MAX 42.3 km/h` |
| 3 | 0x08 | Время движения | `MOV TIME 1:12:36` |
| 4 | 0x10 | Одометр | `MOV ODO 1234.5 km` |

`PageCarousel` (домен, тестируется на хосте):

* хранит маску включённых страниц и порядок (`page_order[5]`);
* переключение по `page_switch_period_s` (1…60, по умолчанию 4);
* при `auto_page_switch = false` показывает `pinned_page`;
* если маска пуста — принудительно включает страницу 0 (защита от «пустого экрана»);
* при переключении страницы форсирует перерисовку вне обычного такта;
* текущая скорость и заряд не являются страницами и остаются на экране постоянно.

### 8.4. Частота обновления и питание дисплея (ТЗ §7)

| Состояние | Частота |
| --- | --- |
| `MOVING` | 4 Гц |
| `SHORT_STOP` / `PAUSED` / `IDLE` | 1 Гц |
| Дисплей выключен | 0 (никаких I²C-транзакций) |

Приглушение выполняется после половины `display_timeout_s` командой
`u8g2.setContrast(20)`. Выключение по полному тайм-ауту:
`u8g2.setPowerSave(1)` + пропуск рендера. Сейчас включение реализовано по корректному
импульсу колеса: `u8g2.setPowerSave(0)`, восстановление контраста и принудительная
перерисовка. После реализации BLE теми же действиями будут обрабатываться подключение,
запись конфигурации и команда теста дисплея. Значение тайм-аута 0 запрещает и
приглушение, и выключение.

Яркость (ТЗ §7.4): процент 1…100 → контраст SSD1306 0…255 по линейной шкале с нижним
порогом читаемости: `contrast = 8 + (pct * 247) / 100`; применяется через `u8g2.setContrast()`.

### 8.5. Отказ дисплея

При ошибке I²C (`u8g2.begin()` вернул 0 или NACK): `display_ok = false`, устройство
продолжает считать поездку и работать по BLE (деградация без остановки), флаг уходит
в телеметрию и диагностику. Повторная попытка инициализации — раз в 30 с.

## 9. BatteryManager

### 9.1. Измерение

Super-nRF52840: внешний делитель подключён как BAT+ → 1 МΩ → P0.31 → 1 МΩ → GND.
P0.31 — задняя площадка и logical pin 32 профиля XIAO. Штатные позиции NPR1/NPR3
конкретной платы не дали достоверных показаний и не используются.

```cpp
analogReference(AR_INTERNAL_2_4);   // опорное 2.4 В (0.6 В × gain 1/4)
analogReadResolution(12);           // 0..4095
// внешний делитель постоянно подключён; снять серию из 16 выборок с P0.31
```

Пересчёт:
```text
v_adc_mv = raw * 2400 / 4095
v_bat_mv = v_adc_mv * DIVIDER_NUM / DIVIDER_DEN        // ≈ ×2.96
v_bat_mv = (v_bat_mv * cal_scale_permille) / 1000 + cal_offset_mv   // калибровка (ТЗ §2.5)
```

Процедура измерения: 16 выборок, отбрасывание min/max, среднее по остальным.

### 9.2. Фильтрация (ТЗ §8.2)

* EMA по напряжению: `v_filt = v_filt + (v_new - v_filt) / 8`; при старте `v_filt = v_new`
  (мгновенная инициализация вместо «подъёма от нуля»).
* Процент считается раз в 10 с из `v_filt` по таблице OCV Li-Po (кусочно-линейная,
  домен `BatteryModel`, без float — целочисленная интерполяция).
* **Гистерезис/монотонность**: отображаемый процент может расти только при активной
  зарядке; иначе допускается только снижение. Это выполняет требование «не допускается
  резкое изменение уровня из-за одиночного измерения».
* Под нагрузкой (OLED включён) напряжение просажено; при `display_on` применяется
  компенсация `+ir_drop_mv` (по умолчанию 25 мВ, в калибровке).

### 9.3. Таблица SoC (ориентировочная, уточняется на реальном АКБ)

| В, мВ | 4200 | 4100 | 4000 | 3900 | 3800 | 3700 | 3650 | 3600 | 3500 | 3400 | 3300 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| % | 100 | 92 | 82 | 68 | 52 | 38 | 28 | 20 | 10 | 4 | 0 |

### 9.4. Статус зарядки и порог

* Статус зарядки Super-nRF52840 аппаратно недоступен и всегда `CHARGE_UNKNOWN`; VBUS
  используется только как разрешение роста отображаемого процента.
* `low_battery` = `pct <= low_battery_pct` (5…50, по умолчанию 20) с гистерезисом +3 %
  на снятие флага. Приводит к предупреждению на экране и флагу в телеметрии (ТЗ §8.3).
* `critical_battery` (≤ 5 %) → немедленная запись одометра и настроек (ТЗ §9.2).

## 10. StorageManager

### 10.1. Носитель и раскладка

`Adafruit_LittleFS` на внутренней Flash (InternalFS). Два независимых набора данных:

| Файл | Содержимое | Частота записи |
| --- | --- | --- |
| `/cfg_a`, `/cfg_b` | Конфигурация (48 байт + заголовок) | Редко (по BLE-записи) |
| `/odo_a`, `/odo_b` | Одометр + агрегаты | Часто (каждые 500 м) |
| `/diag` | Счётчики перезагрузок, последняя ошибка | При старте / при ошибке |

### 10.2. Формат записи (A/B + CRC, ТЗ §9.3)

```cpp
struct RecordHeader {
    uint32_t magic;      // 'BKCP' = 0x50434B42
    uint16_t version;    // версия структуры данных
    uint16_t payload_len;
    uint32_t sequence;   // монотонный счётчик записи
    uint32_t crc32;      // CRC32 полезной нагрузки
};  // 16 байт
```

Алгоритм записи (атомарно):
1. Определить слот с **меньшим** `sequence` (он будет перезаписан).
2. Записать в него `header + payload`, `sequence = max_seq + 1`.
3. `file.flush()`/`close()`. Питание может пропасть в любой момент — второй слот цел.

Алгоритм чтения:
1. Прочитать оба слота, проверить magic/version/CRC.
2. Выбрать валидный слот с максимальным `sequence`.
3. Оба слота невалидны → загрузить defaults, поднять флаг `config_restored_to_defaults`,
   записать defaults в слот A (ТЗ §9.3).
4. `version` меньше текущей → выполнить миграцию (`migrate_v1_to_v2(...)`), затем сохранить.

### 10.3. Политика записи одометра (ТЗ §9.2)

Запись **не** после каждого оборота. Триггеры:

| Триггер | Условие |
| --- | --- |
| По дистанции | `odo_mm - odo_saved_mm >= odometer_save_interval_m * 1000` (по умолчанию 500 м) |
| По остановке | Переход `MOVING → PAUSED` + 30 с без движения |
| Перед сном | Любой переход в `IDLE_DISPLAY_OFF` / `DEEP_SLEEP` |
| По команде BLE | `CMD_FORCE_SAVE` |
| Критический заряд | `pct <= 5 %`, однократно |
| Отключение USB / перед reboot | В обработчике команды `CMD_REBOOT` |

Оценка ресурса: при интервале 500 м и пробеге 10 000 км/год → 20 000 записей/год на два
слота = 10 000 циклов на слот. Ресурс nRF52840 Flash ≥ 10 000 циклов на страницу, LittleFS
дополнительно распределяет износ → запас достаточен. Дополнительная защита: запись
пропускается, если данные не изменились (`sequence` не растёт впустую).

### 10.4. Что сохраняется (ТЗ §9.1)

Конфигурация: окружность колеса, лимит скорости, параметры фильтрации (debounce, фронт,
инверсия), тайм-аут остановки, тайм-аут дисплея, тайм-аут сна, яркость, период карусели,
маска и порядок страниц, имя устройства, калибровка АКБ, порог низкого заряда, единицы
измерения, флаги BLE, версия структуры.
Счётчики: одометр (мм), общее число оборотов, счётчик перезагрузок.

**Поездка (trip) не сохраняется** между перезагрузками сверх одометра: по ТЗ §42.6
обязательна сохранность *дистанции* (одометра). Опционально (feature-флаг
`FEATURE_TRIP_PERSIST`) можно сохранять trip вместе с одометром, чтобы поездка выживала
перезагрузку — решение зафиксировано в ADR-006.

## 11. BleManager

Полный контракт — в [`protocol/ble-protocol.md`](../protocol/ble-protocol.md).
Здесь — только реализация на стороне прошивки.

### 11.1. Стек

Adafruit Bluefruit (SoftDevice S140). Роль: **Peripheral**.

```cpp
Bluefruit.begin();
Bluefruit.setTxPower(4);                 // 4 dBm: компромисс дальность/потребление
Bluefruit.setName(cfg.device_name);      // по умолчанию "BikeComp-XXXX" (4 hex из serial)
Bluefruit.Periph.setConnInterval(12, 48);// 15..60 мс
Bluefruit.Security.setIOCaps(false,false,false); // Just Works
Bluefruit.Security.setMITM(false);
```

### 11.2. Характеристики и их обслуживание

| Характеристика | Свойства | Обработка |
| --- | --- | --- |
| Device Info | Read | Значение формируется при `begin()` и при каждом чтении (uptime) |
| Telemetry | Read, Notify | `task_ble_notify` 1 Гц при наличии подписки; 0.2 Гц если подписки нет |
| Config Read | Read, Notify | Notify при любом изменении конфигурации |
| Config Write | Write w/ Response | Валидация → сохранение → применение → результат |
| Command | Write w/ Response | Разбор, токен подтверждения, исполнение |
| Command Result | Read, Notify | Результат последней команды/записи |
| Error Log | Read, Notify (опц.) | Кольцо из 16 последних событий |

### 11.3. Правила обработки записи (ТЗ §15)

Колбэк записи выполняется в контексте SoftDevice-события — **тяжёлые операции запрещены**.
Реализация: колбэк только копирует payload в очередь `PendingWrite` и ставит флаг;
валидация, запись во Flash и применение выполняются в `AppController` в основном цикле,
после чего отправляется Command Result. Это исключает работу с Flash из BLE-контекста.

Порядок обработки конфигурации:
1. Проверить `struct_version` и длину.
2. Прогнать `ConfigValidator` по всем полям (диапазоны из ТЗ §31).
3. При первой ошибке — отклонить **весь** пакет (транзакционность), вернуть
   `status = ERR_RANGE` + `field_id` нарушенного поля.
4. Сохранить, применить (`applyConfig()` перенастраивает ISR-фронт, контраст, тайм-ауты).
5. Отправить `Command Result` + notify новой конфигурации.

### 11.4. Реклама (ТЗ §10.3)

* Advertising payload: Flags + 128-битный Service UUID (17 байт). Имя устройства — в
  Scan Response (31 байт ограничение основного пакета).
* Быстрая реклама 30 мс в течение 30 с после старта/пробуждения, далее медленная 1000 мс
  без ограничения времени (`ble_always_advertise = true` по умолчанию).
* При `ble_always_advertise = false` реклама останавливается через 5 мин простоя и
  возобновляется при движении.

### 11.5. Безопасность (ТЗ §17)

* LESC pairing + bonding, Just Works (нет ввода/вывода на устройстве).
* Окно сопряжения: **5 минут** после включения. Далее принимаются только bonded-устройства;
  новые запросы pairing отклоняются. Повторное открытие окна: команда через USB-Serial
  (`open-pairing`), либо `CMD_FACTORY_RESET`.
* Требование шифрования: `Config Write` и `Command` — только по зашифрованному соединению
  (`SECMODE_ENC_NO_MITM`). `Device Info` доступен без шифрования (нужен для проверки
  версии протокола до сопряжения).
* Для прототипа — `FEATURE_OPEN_PAIRING=1` (постоянная возможность сопряжения), в релизе 0.

## 12. Диагностика и надёжность

### 12.1. Счётчики (в Device Info / Diagnostics)

`uptime_s`, `boot_count`, `reset_reason` (из `NRF_POWER->RESETREAS`), `free_heap`,
`min_free_heap`, `raw_pulse_count`, `valid_pulse_count`, `rejected_*`, `isr_overflow`,
`flash_write_count`, `flash_error_count`, `i2c_error_count`, `late_task_count`,
`ble_disconnect_count`, `last_error_code`.

### 12.2. Watchdog

Аппаратный WDT с таймаутом 8 с, кормится в `task_watchdog`. Если основной цикл завис —
перезагрузка, `reset_reason = WATCHDOG`, счётчик перезагрузок инкрементируется. Данные
одометра теряются максимум на последние ≤ 500 м.

### 12.3. Self-test (`CMD_START_DIAGNOSTIC`)

Последовательно: I²C-скан адреса дисплея → тестовый паттерн → чтение уровня Холла →
измерение АКБ → чтение/запись тестового файла FS → отчёт в `Command Result` (битовая маска
результатов подтестов).

### 12.4. Отладочный вывод

`Serial` (USB CDC) с уровнями `ERROR/WARN/INFO/DEBUG`, компилируемыми по `LOG_LEVEL`.
В релизной сборке — только `ERROR`. Логирование **никогда** не вызывается из ISR.
Serial-консоль дополнительно поддерживает служебные команды: `open-pairing`, `dump-config`,
`reset-odo`, `selftest` (только при подключённом USB).

## 13. Инициализация (последовательность `setup()`)

```text
1.  Watchdog: конфигурация (не запускать до конца init)
2.  Serial (не ждать подключения!), логирование версий
3.  board_pins: конфигурация GPIO, INPUT_PULLUP на пине Холла
4.  StorageManager.begin() → чтение конфига (или defaults) и одометра
5.  ConfigValidator.clamp() — на случай устаревших/битых значений
6.  BatteryManager.begin() → первое измерение, мгновенная инициализация EMA
7.  DisplayManager.begin() → splash: имя, версия FW, одометр, заряд (1.5 с, неблокирующе)
8.  WheelSensor.begin() → attachInterrupt с активным фронтом из конфига
9.  BleManager.begin() → сервис, характеристики, реклама (быстрая, 30 с)
10. Scheduler.begin() → регистрация задач
11. Watchdog.start(8000)
```

Критично: не блокировать старт ожиданием Serial или BLE — устройство должно быть
работоспособно на велосипеде без телефона и компьютера.
